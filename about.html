About

Telos Research Group helps companies build fleets of coding agents that can be trusted with real systems.

Most teams putting agents on their codebase end up choosing between two bad options. Let the agent work unsupervised, and you are merging a diff nobody watched get written. Review every change by hand, and you have capped the whole thing at the throughput of one reader — which is the speed you already had.

There is a third option, and it is structural rather than clever: force every non-trivial change through the same shape, every time. Facts get established before anyone plans. A human approves the plan — its shape, its slices, and the explicit list of what is not being done — before any code exists. A reviewer working in a context that never saw the code being written gets real authority to reject it. And nothing is called done on the strength of a claim: the close is checked against git, not against a status file that only knows what it was told.

That structure is what we build, adapt, and hand over. How it works lays out the three layers; Code is the working reference implementation, open and readable rather than described in a slide.

What we will tell you not to do

Most changes should not go through a graph at all. One file, one bug, one endpoint, or anything whose slices would touch the same files — those belong in a single loop: one agent, one context, done. Orchestration costs real tokens and real wall-clock, and it only earns that back when the slices are genuinely independent and the verification genuinely needs eyes that never saw the code written.

A firm that sells you orchestration for every change is selling you overhead. The rough line we use is three or more independent slices, or a change you would not merge unreviewed.
